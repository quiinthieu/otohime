## The failure: touch on the tonearm

- `turntable.tsx` and the README say the arm takes touch ("touch included: only the arm has touch-action: none"). The plan's item 3 and the brief ("draggable tonearm via pointer events, touch support") ask for it.
- Chrome applies `touch-action` only to elements with a CSS box. Inside an `<svg>`, the `<g class="tonearm">` and its `line`/`rect` children do not count. The hit-tested `line.arm-grab` computes `touch-action: auto`. So the browser takes the gesture as a pan and cancels the pointer.

Controls I ran, all on production at 390 px with CDP touch:

| Variant (injected by the test only) | pointercancel | scroll | phase |
| --- | --- | --- | --- |
| As delivered | 1 | 0 sideways, −76 px down | loaded |
| `.tonearm * { touch-action: none }` | 1 | −87 px down | loaded |
| `.turntable svg { touch-action: none }` | 0 | 0 | playing |
| Non-passive `touchstart` listener on `.tonearm` with `preventDefault()` | 0 | 0 | playing |
| Non-passive `touchmove` listener on `.tonearm` with `preventDefault()` | 0 | 0 | playing |

So this is a code defect, not a harness artefact. The software engineer's touch evidence covered the sleeve drag and the crate swipe, not the arm. The keyboard slider and the seek bar still work, so a touch user can still play and seek. The drag itself is broken.
