# Fortune data and reducer contract

`buildFortuneTargets()` in `lib/fortune-targets.ts` accepts plain collections. The server adapter for task 5 supplies `site.projectList`, `site.notes`, `site.sketches`, `site.songs`, current `listSongs()` rows as `ownerSongs`, and Gazette `ARTICLES`. It may pass an empty owner song list if that read fails. The pure builder has no browser, database, or network dependency. It preserves source order, then removes duplicate target ids or hrefs. Adding or removing content updates the pool on the next server read; no separate fortune catalogue exists.

Each target is `{ id, label, href, kind }`. Project cards with a safe local `href` use that route. A project without `href` uses `/projects#${projectTargetId(title)}`; external or malformed hrefs are excluded. Notes use `/notes#${noteTargetId(date)}`, sketches use `/sketches#${sketchTargetId(src)}`, songs use `/music#${songTargetId(video)}`, and Gazette articles use `/articles/${slug}`. All target hrefs are local. Blank and malformed identities are excluded. An empty pool reveals `{ id: "fortune-fallback", label: "Projects", href: "/projects", kind: "project" }`.

Task 5 must set the exact DOM `id` from the shared helpers on each displayed **note date**, **sketch source**, and **song video id** item. For missing-href projects it must set `projectTargetId(title)` on the project card. These IDs are UTF-8 hex encodings with distinct prefixes. They do not use array indexes or lossy slugs, so reordering cannot change them. Current listing components have no such item fragments yet; task 5 owns rendering them. Existing routes remain the destination for projects with hrefs and for articles.

`createFortuneState(seed, targets)` snapshots and shuffles safe targets without changing caller data. The reducer accepts only phase-valid actions: `choose-colour` → `tick` or `finish-counting` → `choose-first-number` → `tick` or `finish-counting` → `choose-final-number` → `reveal`. `reset` supplies a fresh seed and target snapshot. `pinch` changes the visible axis only outside counting and reveal; it cannot choose or advance a phase. `tick` advances exactly one count and alternates the axis. `finish-counting` applies the same ticks immediately. Invalid, repeated, or early actions return the same state object.

Colours are coral (5 letters), blue (4), mint (4), yellow (6). Axis 0 exposes 1, 3, 5, 7; axis 1 exposes 2, 4, 6, 8. The UI should call `visibleNumbers(state)` for each numbered choice, not hardcode a quartet. Count colour letters, choose an exposed first number, count that many ticks, choose an exposed final number, then reveal. The seeded shuffle and selected colour/numbers determine the target. Identical seed, snapshot, and actions reproduce it; a new seed can alter the order. The UI owns timing, motion preference, sound, and presentation.
