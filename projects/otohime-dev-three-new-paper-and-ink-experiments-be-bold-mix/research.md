# Research preserved from report rep-5449

Research for `pm-293` (`run-9228`):

## Repository facts
- Stack: Next 16.4.2 and React 19.3; `ViewTransition` is already used on `/play` and `/projects`.
- `content/history.json` holds only the newest 200 non-merge commits (`sha`, `date`, `plan`, `task`, `subject`, `files`, `added`, `removed`, `areas`), so it cannot cover a full 12-month calendar year on its own.
- Models per role are not stored in the repository's existing `content/history.json`.
- Projects in `content/site.ts` (`site.projectList`) have `title`, `note`, `href`, `status` (`"building" | "live" | "shelved"`), and `colour`, but no `started`, `shipped`, or `abandoned` fields yet.

## Recommended design across the three experiments

### Shared foundation: Build-time yearly digest (`content/yearly-log.json`)
- Build a shared yearly digest (`content/yearly-log.json`) generated by a script like `scripts/history-index.ts` (`scripts/yearly-log.ts`), with a committed fallback because production checkouts can be shallow (`depth-1`).
- Aggregate full git commit history by calendar month (`01`..`12`), combined with `content/site.ts` project records and notes and `content/ledger.json` activity counts, so both the Hanafuda monthly card backs and project timelines read one validated static JSON index.

### 1. Daruma Project Board (on `/projects`)
- Extend project records in `content/site.ts` with `started`, `shipped`, `lastActivityAt`, and optional `abandoned` fields.
- Build a hand-drawn red SVG Daruma doll component with a `stroke-dashoffset` brush-stroke left eye (painted when a project starts) and right eye (painted when it ships), plus a CSS/spring wobble on hover/focus that rolls back upright.
- Show it as a Shelf view on `/projects` alongside the existing Cartridge view, placing unfinished dolls on a shelf.
- Default `abandoned` means no activity for 90 days and not shipped (or explicitly shelved/abandoned).
- The year-end "Daruma Kuyo" ink-fire ceremony is a toggle with a `?kuyo=1` query parameter and an injected clock so unit and browser tests prove it immediately without waiting for December.

### 2. Making-of Emaki (`/making-of`)
- Group commit history by the `pm-NNN` commit prefix to form scenes.
- Provide a generator/validator script (`scripts/making-of-index.ts`) and a reviewed snapshot (`content/making-of.json`) containing public fields only: plan id, title, date, commit SHA/link, and public model IDs per role (`research`, `product_owner`, `software_engineer`, `quality_engineer`).
- Use a sticky tall wrapper that maps vertical scroll to horizontal translation, and CSS `animation-timeline` where supported, with scroll-scrubbed parallax layers.
- Render a semantic ordered list (`<ol>`) for assistive tech and no-JS users. `prefers-reduced-motion` turns parallax off.
- Draw four reusable ink figures (researcher, product owner, software engineer, quality engineer) passing a handscroll along.

### 3. Hanafuda Koi-Koi (`/play/hanafuda`)
- Phase the implementation cleanly:
  - **Engine & Yaku**: pure deterministic reducer with seeded RNG, 48-card deck across 12 monthly flower suits, greedy CPU opponent with no LLM, 3-round default match, and table-driven tests for all 12 standard yaku (`Goko`, `Shiko`, `Ame-Shiko`, `Sanko`, `Inoshikacho`, `Tane`, `Akatan`, `Aotan`, `Tan`, `Kasu`, `Hanami-zake`, `Tsukimi-zake`).
  - **Board UI, SVG Deck, View Transitions & Audio**: 48 SVG cards drawn from a shared ink-and-washi base frame, drag-to-match plus tap and keyboard navigation, View Transitions on deal/flip, and opt-in WebAudio paper-shuffle sound via the existing site sound toggle.
  - **Hanko & Monthly Card Backs**: hanko stamp yaku announcements and brush-stroke `"Koi-koi?"` prompt backed by real `aria-live` text; each month's card back can be flipped to reveal what the owner shipped that month from `content/yearly-log.json`.

## Resolved defaults
- Koi-Koi match length: 3 rounds (`month` 1..3 by default, configurable).
- Daruma abandonment threshold: 90 days without activity and not shipped.
- Making-of Emaki model IDs: public model identifiers shown per role.
- Note on plan structure: while `rep-5449` suggested splitting into three plans, current platform rules forbid plan splitting (`after_plan_id` / multi-plan splits removed), so all tasks remain in one parallelized DAG on `pm-293`.
