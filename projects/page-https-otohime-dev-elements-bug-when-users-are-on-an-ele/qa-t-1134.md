## Findings (non-blocking, for the product owner)

1. **On macOS, the committed probe's steady-table checks cannot fail.** Run against the pre-fix build c2660b7, `scripts/probe-elements-dialog.mjs` reports 8 ok, 2 failed. Only the two no-lift checks fail (`matrix(1.0605…)` at +150 ms, `matrix(1.08…)` at +450 ms). All three steady-table checks pass, because Chromium on macOS keeps overlay scrollbars. The probe works where Chromium draws classic scrollbars: the engineer's pre-fix run measured the same +3/+9 px. To harden it, launch with `--disable-features=OverlayScrollbar,OverlayScrollbars` and add a precondition that `document.documentElement.clientWidth < innerWidth`, so an overlay-scrollbar run reports `not ok` instead of passing for nothing.
2. **Fixture trap.** Faking classic scrollbars by injecting `::-webkit-scrollbar { width: 15px }` gives the wrong answer. In overlay mode Chromium ignores `scrollbar-gutter` for custom scrollbars: a minimal page measured 1351 → 1366 with and without the gutter. Under that fixture, production looked unfixed. Use the feature flag instead.
3. **Mouse open, then Esc.** If the dialog was opened by a mouse click and closed with Esc while the pointer is still parked over the opener, `.table[data-settle] .cell:hover` (specificity 0,3,0) also holds the opener's `:focus-visible` lift until the pointer moves. A keyboard-only open and close keeps the lift (row above). This matches "no cell lifts until the pointer moves", and I do not count it as a defect.
